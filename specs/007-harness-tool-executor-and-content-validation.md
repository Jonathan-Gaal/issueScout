# 007 — Harness tool executor and content validation

## [SPEC]

- **Objective**: Build the two harness pieces the run loop (spec 008) wires together: `toolExecutor.ts` (the model-facing `github_issue_research` tool definition + the function that executes a validated tool call against the `GitHubClient`, enforcing `MAX_SEARCHES`/`MAX_CANDIDATE_READS` per-run counters and refusing further calls of a kind once hit), and `validateContent.ts` (TRD §2 step 7 — strips invented labels/un-retrieved related-issue numbers/non-sourced URLs from a validated `ModelReport`, recording each into `coverage.removedByValidation`). The per-user rate limiter (`rateLimiter.ts`, US-2's `RUNS_PER_USER_PER_HOUR` criterion) is split into spec 007b to stay within the 5-file cap.
- **Inputs/Outputs**: Tool schema exposed to the model per TRD §3.3: `github_issue_research` with `operation: "read" | "search"` and no `owner`/`repo` parameter at all (schema-level fact, not a convention) — `read` takes an issue number, `search` takes a query string. `validateContent.ts` operates on a zod-validated `ModelReport` (spec 004's output) plus the run's actual retrieved-labels list, retrieved-issue-numbers set, and retrieved-URLs set (all harness-tracked, supplied by spec 008's caller) and returns a cleaned `ModelReport` plus a `string[]` of removal descriptions for `coverage.removedByValidation` (TRD §3.1).
- **Design Pattern**: none beyond what TRD's 9-step lifecycle already specifies — each of these three files is a pure-ish function (given a `GitHubClient`/run counters/a `ModelReport`, produce a result) rather than a class hierarchy; matches the plan's calibration against over-engineering.
- **Bounded-AI boundary**: Entirely deterministic. The content *being* validated originated from a model (upstream, spec 008), but the stripping/comparison logic itself is pure code — this is the BOUNDED-AI rule in action: the model may produce a label name, but whether that label is accepted is a deterministic set-membership check against the real label list, never a second model judgment call.
- **Verification Oracle**: `npx vitest run tests/unit/toolExecutor.test.ts` — new unit tests against a fake `GitHubClient`: the 4th search call in one run is refused (`outcome: "refused"`) once `MAX_SEARCHES=3` is reached, without calling the fake client's `searchIssues` a 4th time; the 6th candidate read is refused once `MAX_CANDIDATE_READS=5` is reached; the tool definition object passed to the model contains no `owner`/`repo` property at any nesting level (a direct object-shape assertion, not just a behavioral test — guards the architectural injection defense TRD §5/CLAUDE.md calls out). `npx vitest run tests/unit/validateContent.test.ts` — new unit tests: a `ModelReport` fixture with a `suggestedLabels` entry naming a label not in the supplied real-label-list is stripped and appears in the returned `removedByValidation` array; a `relatedIssues` entry citing a number never added to the run's retrieved-issue-numbers set is stripped and recorded; a report with no invalid content passes through unchanged with an empty `removedByValidation`.
- **Intellectual Control**: Refusing (returning a typed `refused` outcome) rather than throwing when a limit is hit is what lets the harness (spec 008) tell the model "finish with what you have" (TRD §2 step 5) instead of crashing the run — this distinction is tested explicitly (`outcome: "refused"` vs `"error"`) because conflating them would make `coverage.searchesFailed` (a real GitHub failure) indistinguishable from "the harness said no," corrupting PRD §4's failure-transparency metric. The tool schema's object shape being asserted directly (not just behaviorally inferred) is what makes "model never supplies owner/repo" a build-time-checkable fact rather than an assumption that holds only as long as nobody edits the schema carelessly later.
- **Constraints**: No new dependency. `validateContent.ts` must not mutate its input `ModelReport` in place — return a new object — so the pre-validation report remains available for any debugging/logging that needs to compare before/after (useful given `coverage.removedByValidation` is itself a diff artifact).
- **Edge Cases**: A `ModelReport` with zero items in any of `suggestedLabels`/`relatedIssues`/`evidence` validates cleanly with nothing to strip — an empty array is not itself invalid content. A URL in `evidence[].sourceUrl` that happens to be a syntactically valid GitHub URL but was never actually constructed by this run's own tool calls is stripped — "sourced from retrieved data" is checked against the run's own retrieval set, never by re-fetching or by trusting the URL's shape alone (TRD §2 step 7, Build Spec §8.1 step 7).
- **UI States**: N/A — no UI files.
