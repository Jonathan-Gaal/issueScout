# 008 — Harness run loop (`runHarness.ts`)

## [SPEC]

- **Objective**: Wire every prior harness piece (GitHub client, model provider, zod schema, tool executor, content validator, rate limiter, system prompt) into the single `runHarness(issueUrl, userId)` function implementing TRD §2's 9-step lifecycle end to end — input checks, fetch, turn loop with limit enforcement, structure validation with one retry, content validation, coverage assembly from harness counters only, and the forced `proposedActions = []` overwrite. This is the file US-2/US-3/US-4's acceptance criteria are actually exercised against, and the file spec 013's T1/T2/T3/T6/T8/T9/T10 acceptance tests target.
- **Inputs/Outputs**: `runHarness(params: { issueUrl: string; userId: string }): Promise<{ status: "completed" | "stopped" | "failed"; report?: Report; errorCode?: ErrorCode }>` — the typed terminal-value contract TRD §4 requires ("no path returns undefined/null as the terminal value"). Internally implements, in order, Build Spec §8.1 steps 1-9 (step 10 is Phase 2, not built): (1) rate-limit + URL/repo checks → `invalid_url`/`repo_not_allowed`/`run_rate_limited`, no model call; (2) fetch issue/comments/labels → `not_found`/`is_pull_request`/`issue_too_long`, no model call; (3) build initial messages (system prompt + issue/comments marked untrusted + label list + tool def); (4-5) turn loop bounded by `MAX_MODEL_TURNS=15`/`MAX_RUN_SECONDS=120`, tool calls routed through spec 007's executor; (6) zod structure validation via spec 004's schema, one retry (`MAX_FORMAT_RETRIES=1`), else `model_output_invalid`; (7) content validation via spec 007's `validateContent`; (8) `coverage` assembled from this function's own counters, never from model output; (9) force `proposedActions = []`, persist via spec 009's data layer (referenced, not redefined), return.
- **Design Pattern**: A straightforward state-machine loop (turn counter + elapsed-time check each iteration), matching TRD §2's 9 numbered steps 1:1 — explicitly not a generic "agent framework" abstraction, since Build Spec §3 forbids multi-agent/multi-tool generality and this harness has exactly one tool and one model role by design.
- **Bounded-AI boundary**: This is the one file where the boundary is sharpest and most load-bearing: the model generates `summary`/`category`/`categoryReason`/`priority`/evidence narration/`suggestedLabels`/`relatedIssues` assessments — all qualitative/narrative judgment. Everything numeric or decisive is computed by this file's own code: `coverage.searchesRun`/`searchesFailed`/`candidatesRead`/`stopReason` are harness counters, never model-reported (TRD §3.1, explicit "NEVER by the model"); `proposedActions` is force-overwritten to `[]` regardless of model output; which labels/related-issues/URLs survive content validation is a deterministic set-membership check (spec 007), never a second model pass. A model may narrate; it may never produce a number, a limit decision, or the final coverage/stop-reason record — this is the BOUNDED-AI cross-cutting rule's canonical application in this codebase.
- **Verification Oracle**: `npx vitest run tests/harness/runHarness.test.ts` — new unit/integration tests against fake `GitHubClient` and fake `ModelProvider` implementations (no real network): (a) a clean fixture run returns `status: "completed"` with a well-formed `Report` whose `coverage.stopReason === "completed"`; (b) a fake model that requests searches forever is stopped at `MAX_MODEL_TURNS` or `MAX_RUN_SECONDS`, returning `status: "stopped"` with `coverage.stopReason` naming the limit and a non-empty partial report — never `status: undefined`/a thrown exception; (c) `report.proposedActions` is `[]` even when the fake model's raw output includes non-empty `proposedActions` entries — the literal forced-overwrite assertion; (d) a fake model whose first output fails zod validation and whose second (retried) output also fails returns `status: "failed", errorCode: "model_output_invalid"`; (e) a forced GitHub rate-limit mid-run results in `coverage.searchesFailed >= 1`, never a report implying zero matches were found. This single test file is this spec's primary oracle; spec 013 later adds the formal T-numbered acceptance tests reusing this same `runHarness` entry point.
- **Intellectual Control**: Every one of TRD's 9 steps is a named, independently-reasoned block in this function rather than inlined ad hoc — this is what keeps "a stopped run must return a partial report or a clear error, never a blank result" (TRD §4 Reliability) checkable by code review and by the oracle above, rather than relying on every early-return path happening to remember the rule. The turn loop's limit checks run *before* making the next model/tool call, not after, so the harness never exceeds `MAX_MODEL_TURNS`/`MAX_RUN_SECONDS` by even one extra call.
- **Constraints**: No new dependency — this spec is pure orchestration of specs 002-007b's already-built pieces plus spec 009's data layer (persistence happens here, at the end of a run, not scattered across the loop). No GitHub write call exists anywhere in this file, in any code path — Phase 1's read-only invariant (PRD §3/§9) is enforced by this file simply never importing a write-capable function, since none exists yet (spec 003 built read-only only).
- **Edge Cases**: A run that fails at step 1 or 2 (before any model call) never constructs a model message array at all — not merely "doesn't send it," but doesn't build it, confirmed by the fake `ModelProvider`'s `.complete()` being asserted never called on these paths (mirrors T10's exact pass condition). A `containsEmbeddedInstructions: true` model output is passed through unmodified into the final report (it's a reviewer signal, not something the harness acts on) — the actual defense against the embedded instruction is architectural (no write tool exists), confirmed by this spec's test *not* needing to assert anything GitHub-write-related, because there is nothing to assert against. An elapsed-time check that lands exactly at `MAX_RUN_SECONDS` stops the run (boundary case, `>=` not `>`).
