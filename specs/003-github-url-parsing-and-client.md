# 003 — GitHub URL parsing and read-only GitHub client

## [SPEC]

- **Objective**: Build the pure URL-parsing function that classifies a submitted `issueUrl` (valid issue in `APPROVED_REPO` / wrong repo / is-a-PR / malformed), and the `GitHubClient` interface + implementation providing the harness's only path to GitHub — `getIssue`, `getComments`, `getLabels`, `searchIssues` — all read-only, with the model never supplying `owner`/`repo` itself.
- **Inputs/Outputs**: GitHub REST endpoints per TRD.md §3.3 table (`GET /repos/{owner}/{repo}/issues/{number}`, `.../comments`, `.../labels`, `GET /search/issues`). Limits enforced here per TRD §3.3: `MAX_COMMENTS_PER_ISSUE=20`, `REQUEST_TIMEOUT_SECONDS=20`, `MAX_RETRIES_PER_REQUEST=1` (network failures only, never on 4xx — plan's explicit rule), `MAX_SEARCH_RESULTS=10`. `ModelReportSchema`'s `relatedIssues`/`evidence` later consume this client's output shape — this spec owns `GitHubIssue`/`GitHubComment`/`GitHubLabel`/`SearchCandidate` types, referenced (not redefined) by spec 007/008.
- **Design Pattern**: Interface + implementation (plan's `GitHubClient` interface) so a fake implementation can back harness tests without a real network call — this is the test-mocking seam, not a speculative abstraction (same interface is used for exactly one real implementation; the "pattern" earns its keep because spec 013's acceptance tests inject a fake one against this exact interface).
- **Bounded-AI boundary**: Entirely deterministic. No model involvement in URL parsing or GitHub fetch/parse logic.
- **Verification Oracle**: `npx vitest run tests/unit/urlParsing.test.ts` — new unit tests covering: a valid `calcom/cal.diy` issue URL parses to `{ owner, repo, number }`; a URL in a different repo returns `repo_not_allowed`; a PR URL (`/pull/`) returns `is_pull_request`; a malformed URL returns `invalid_url`. `npx vitest run tests/unit/githubClient.test.ts` — new unit tests against a mocked `fetch`: `getComments` truncates at 20 and sets `truncated: true` on a 21-comment fixture; `searchIssues` filters out any result containing a `pull_request` field and the input issue's own number; a simulated `403`/`429` response causes `searchIssues` to return `{ rateLimited: true }` rather than throwing or returning an empty-but-successful result (guards TRD §3.3's "never silently convert to zero matches" rule at its source).
- **Intellectual Control**: `urlParsing.ts` is pure (no I/O), so its correctness is fully covered by unit tests with no mocking needed — this is the cheapest, most reliable part of the input-validation chain (US-2's `invalid_url`/`repo_not_allowed`/`is_pull_request` criteria) to get exactly right. The client hardcodes `owner`/`repo` from `config.approvedRepo` rather than accepting them as parameters from any caller that might eventually be model-influenced — this is the architectural half of the "model never supplies owner/repo" rule (TRD §3.3, §5); the other half (tool-schema-level enforcement) is spec 007's job, not this one's, but this spec's function signatures are what make that enforcement possible downstream.
- **Constraints**: No HTTP client dependency — native `fetch` + `AbortController` only, per the plan and dependency-triage (a wrapper around two authenticated GETs and a search call does not meet the bar for importing a library). Every network call wrapped in `AbortController` with the `REQUEST_TIMEOUT_SECONDS` timeout; the one retry (`MAX_RETRIES_PER_REQUEST=1`) fires only on network-level failure (timeout, connection reset), never on an HTTP 4xx response (a 404/403 is a validation/auth fact, not a transient fault a retry fixes).
- **Edge Cases**: Issue not found → `getIssue` returns `{ notFound: true }`, never throws (the harness's step-2 `not_found` path, spec 008, depends on this being a typed return, not an exception to catch). A GitHub response that fails to parse as JSON (malformed response, T8's forced-malformed-response case) is caught and surfaces as a typed `{ error: true }`-shaped result, never an uncaught exception that would bubble as a raw stack trace. Pull requests are identified by the presence of a `pull_request` field on the GitHub API response — not by URL shape alone, since `search/issues` returns PRs mixed into issue results.
- **UI States**: N/A — no UI files.
- **Files** (≤5):
  1. `lib/server/github/urlParsing.ts` — new.
  2. `lib/server/github/types.ts` — new (`GitHubIssue`, `GitHubComment`, `GitHubLabel`, `SearchCandidate`, `GitHubClient` interface).
  3. `lib/server/github/client.ts` — new (real implementation).
  4. `tests/unit/urlParsing.test.ts` — new.
  5. `tests/unit/githubClient.test.ts` — new.

**References (≤3):** `lib/server/config.ts` (spec 002, for `config.approvedRepo`/`config.githubReadToken`/timeout constants), `lib/server/errors.ts` (spec 002, for `ErrorCode` values this spec's callers will map to), TRD.md §3.3 (the tool contract table this spec implements).

[FORCES]
1. Typed return values over thrown exceptions for expected failure modes (not-found, rate-limited, malformed) > a single exception-handling path that can't distinguish them.
2. Simplicity > Pattern purity (always present unless explicitly overridden).
