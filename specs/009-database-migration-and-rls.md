# 009 — Database migration: Phase-1 tables + RLS policies on all seven

## [SPEC]

- **Objective**: Write the Supabase Postgres migration creating the four Phase-1 tables (`runs`, `issues`, `tool_calls`, `reports`) and define RLS policies on all seven Build-Spec-§9 tables — the four built this cycle plus `actions`/`approvals`/`eval_results`, whose policies are decided now per SCHEMA.md's instruction even though those three tables aren't created until Phase 2/3. This is PRD §9 finding #4 / US-7's binding requirement, and it is a Crucial Juncture item (data-integrity, auth-adjacent) per the global edge-case-triage skip-the-gate rule — no cheap-sweep-first here, full enumeration from the start.
- **Inputs/Outputs**: Exact column list per SCHEMA.md's per-table sections (`runs`: `id`, `user_id`, `issue_url`, `status`, `stop_reason`, `error_code`, `searches_used`, `reads_used`, `model_turns_used`, `duration_ms`, `finished_at`, `created_at`; `issues`: `id`, `run_id`, `repo`, `number`, `title`, `state`, `url`, `retrieved_at`, `created_at`; `tool_calls`: `id`, `run_id`, `operation`, `arguments`, `outcome`, `error_code`, `duration_ms`, `created_at`; `reports`: `id`, `run_id` UNIQUE, `report` jsonb, `created_at`). Indexes per SCHEMA.md's "Indexes & Performance Notes": `runs(user_id, created_at DESC)`, `tool_calls(run_id)`, `issues(run_id)`, `reports(run_id)` UNIQUE. RLS policy shape per SCHEMA.md's "Row Level Security" section: `runs` scoped `user_id = auth.uid()`-equivalent for SELECT/INSERT/UPDATE (no DELETE policy — nothing in Phase 1 deletes a run); `issues`/`tool_calls`/`reports` scoped via a subquery against `runs.user_id` (they have no direct `user_id` column). `actions`/`approvals`/`eval_results` table *definitions* are not created this cycle (SCHEMA.md explicit "not created this cycle" per table) — only their RLS policy *shape* is decided and documented in this migration's comments for when Phase 2/3 creates them, per SCHEMA.md's instruction not to re-derive it later.
- **Design Pattern**: Plain SQL migration file applied via the Supabase SQL editor directly, no migration-tool dependency (plan's explicit "no migration-tool dependency needed for a 2-person project" calibration) — matches dependency-triage's default-write-it-yourself stance for a one-time DDL script.
- **Bounded-AI boundary**: Entirely deterministic — DDL and RLS policy SQL contain no model-generated content.
- **Verification Oracle**: Two-part, since this is a Crucial Juncture item that must actually be tested, not just declared (SCHEMA.md/US-7: "attempt a read/write as a non-service-role role and confirm denial — this needs to actually be tested once, not just declared in SQL and trusted"): (1) Apply the migration against a real or local Supabase/Postgres instance; `\d runs`, `\d issues`, `\d tool_calls`, `\d reports` in `psql` (or the Supabase table editor) confirm every column/constraint/index from SCHEMA.md exists exactly as specified. (2) A new test (`tests/integration/rls.test.ts`, run with `npx vitest run tests/integration/rls.test.ts`) connects as the Postgres `anon`/non-service-role role (Supabase's standard non-privileged role) and asserts: a `SELECT`/`INSERT` on `runs` with no matching `auth.uid()` claim is denied; a `SELECT` on `issues`/`tool_calls`/`reports` for a run owned by a different `user_id` is denied. This test requires a real Supabase connection (not mockable, since RLS is a database-enforced property) — if no Supabase project is available in the build environment, this test is explicitly marked `skip` with a logged gap in `log.md`, not silently deleted, since an untested RLS policy is exactly the failure mode SCHEMA.md warns against ("a misconfigured RLS policy goes unnoticed until a non-service-key caller actually hits it").
- **Intellectual Control**: Scoping `issues`/`tool_calls`/`reports`'s RLS policies via a subquery against `runs.user_id` (rather than duplicating a `user_id` column onto each child table) matches SCHEMA.md's own design reasoning (those tables relate to `runs` by `run_id`, no direct ownership column) — this is also exactly why the `runs(user_id, created_at DESC)` index matters for RLS policy performance, not just for the `GET /api/runs` list query, per SCHEMA.md's explicit note. Defining all seven tables' RLS *policy shape* now, even for three tables not created this cycle, means Phase 2/3 never has to re-derive this decision under time pressure later — a one-time cost paid here.
- **Constraints**: No ORM, no migration-tool dependency (Prisma/Drizzle/etc. not introduced — `@supabase/supabase-js`'s query builder, already pre-authorized, is sufficient per the plan's own reasoning). This migration file creates only the four Phase-1 tables — it must not create `actions`/`approvals`/`eval_results` table *structures*, only document their intended RLS policy shape in a comment block, since SCHEMA.md is explicit those three are "not created this cycle."
- **Edge Cases**: `runs.user_id` is NOT NULL (SCHEMA.md: "a run with no owner can't be IDOR-checked") — the migration must enforce this at the column level, not just in application code, so a bug that tries to insert an ownerless run fails at the database, not silently. `reports.run_id` carries a UNIQUE constraint — a second report insert for the same run is a constraint violation, not a silent duplicate (SCHEMA.md: "makes 'a run somehow got two reports' a constraint violation instead of a silent data-quality bug"). If no real Supabase/Postgres instance is reachable in this build's environment, the RLS test is skipped with an explicit, logged reason (see oracle above) — never silently passed or deleted.
