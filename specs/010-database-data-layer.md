# 010 — Database data-access layer: client + runs

## [SPEC]

- **Objective**: Build the Supabase client singleton and the `runs` table's typed accessor functions — the harness's (spec 008) and route handlers' (spec 013) primary read/write surface for run records, including the two functions that carry PRD §9 finding #2's ownership-enforcement weight (`getOwned`, `list`). `issues`/`tool_calls`/`reports` accessors are spec 010b, split out to stay within the 5-file cap — `runs.ts` is kept together with the client singleton here because it is the file this spec's oracle most needs to scrutinize (the ownership-query-predicate logic), and splitting it from its own test would weaken that scrutiny.
- **Inputs/Outputs**: Functions this spec must provide (names illustrative, shape fixed by spec 009's schema): `db.runs.create(...)`, `db.runs.updateStatus(...)`, `db.runs.countInLastHour(userId)` (the function `rateLimiter.ts`, spec 007b, expects as its injected count source), `db.runs.list(userId, limit)` (backs `GET /api/runs?limit=`, scoped to `user_id` in the query itself — TRD §4's "ownership check is in the query predicate itself" rule), `db.runs.getOwned(id, userId)` (backs `GET /api/runs/:id`'s ownership check — `WHERE id = :id AND user_id = :userId`, never an unscoped fetch followed by a comparison).
- **Design Pattern**: One file per table (matches the plan's `db/supabaseClient.ts`, `runs.ts`, `issues.ts`, `toolCalls.ts`, `reports.ts` structure) — simple data-access functions, no repository-pattern abstraction beyond what's already natural from one-file-per-table, since there's exactly one real backing store (Supabase) and no swap requirement here (unlike the model/auth provider seams, which do need one).
- **Bounded-AI boundary**: Entirely deterministic. No model-generated content; this layer persists/retrieves data the harness and model already produced.
- **Verification Oracle**: `npx vitest run tests/unit/dbLayer.test.ts` — new unit tests against a mocked Supabase client (the `@supabase/supabase-js` client's `.from().select()/.insert()/.update()` chain mocked, no real network): `db.runs.getOwned(id, userId)` constructs a query with both `id` and `user_id` in its filter — asserted via inspecting the mock's call arguments, not just the return value, since this is the literal implementation of TRD §3.2's ownership contract ("the ownership check is in the query predicate itself"); `db.runs.list(userId, limit)` always includes a `user_id` filter — a call with no `userId` argument is a type error, not a runtime-optional parameter (this is the mechanism-level guarantee behind US-5's "only that user's runs, newest first"). A second integration-style check (manual, logged as part of this spec's completion report, not a CI-blocking oracle): after spec 009's migration is applied to a real Supabase project, one `db.runs.create()` + `db.runs.getOwned()` round-trip succeeds against the real database.
- **Intellectual Control**: Every per-resource read function takes `userId` as a required parameter baked into the query itself — this is deliberately not a two-step "fetch then check ownership in application code" pattern, because that shape is exactly the class of bug PRD §9 finding #2 exists to prevent (a forgotten check after the fetch). Making the ownership filter part of the query's required parameter list means there is no code path that can fetch a run without also constraining by owner — the type signature itself forecloses the mistake.
- **Constraints**: `@supabase/supabase-js` only (pre-authorized); the Supabase client in this file uses the **service-role key**, backend-only, never exposed to any browser-reachable code path (PRD §9, Build Spec §4). No raw SQL string concatenation anywhere — only the query-builder's parameterized methods, satisfying Build Spec §8.2's "model text stored in the database goes through parameterized queries" at the one place such text is persisted (via `db.reports.create`).
- **Edge Cases**: `db.runs.getOwned(id, userId)` for a run that exists but belongs to a different user returns the same "not found" result shape as a run that doesn't exist at all — this file does not distinguish the two cases in its return value (it returns `null`/`undefined` either way), which is what lets the route handler in spec 013 implement TRD §3.2's "never leak existence of another user's run" rule without having to remember to collapse two different signals itself; the collapsing happens here, at the data layer, not as an afterthought in the route.
