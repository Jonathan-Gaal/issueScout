# 013 — API routes: POST/GET /api/runs, GET /api/runs/:id, CORS enforcement

## [SPEC]

This is a Crucial Juncture spec (auth-adjacent: per-resource IDOR enforcement) per the global shared definition — edge-case-triage's skip-the-gate rule applies directly. **Soundwave must run against this spec's diff** per CLAUDE.md's conditional-inclusion rule (the per-run ownership check is exactly its trigger).

## [SPEC] (continued)

- **Objective**: Build the three Phase-1 active route handlers (TRD §3.2) — `POST /api/runs`, `GET /api/runs`, `GET /api/runs/:id` — wiring spec 011's two-check auth, spec 008's harness, and spec 010/010b's data layer together, plus the strict non-wildcard CORS enforcement (PRD §9 finding #5, US-6) applied from this, the first route handler, not deferred to a pre-deploy checklist item.
- **Inputs/Outputs**: Literal contract from TRD.md §3.2, verbatim, no invented shape: `POST /api/runs` — body `{ issueUrl: string }`, returns `{ runId, status, report?, error? }`. `GET /api/runs?limit=` — no body, returns recent runs for the requesting user only, newest first. `GET /api/runs/:id` — no body, returns `{ run, report, actions }` for a run the requesting user owns; for a run that doesn't exist OR exists but isn't theirs, returns the *same* response shape (this spec picks `not_found` consistently, per TRD §3.2's "pick one and apply consistently" instruction — `not_found` is chosen here, not `unauthorized`, so that a non-owned run is indistinguishable from a non-existent one, never hinting "this exists but isn't yours"). Error shape every endpoint: `{ error: { code, message } }` per spec 002's `ErrorCode` map. CORS: `CORS_ALLOWED_ORIGINS` read as a comma-split explicit allowlist from env, checked against the request's `Origin` header on every request to every route in this spec, reject (403, no CORS headers) if not present in the list — no wildcard, no default-allow.
- **Design Pattern**: Thin route handlers — auth check → input validation → delegate to `runHarness`/`db` layer → map result to HTTP response (matches the plan's "thin wiring, last since everything they call is already tested" build-order note). A shared CORS-check helper is called at the top of every handler rather than reimplemented three times (DRY at the function level, per global CLAUDE.md's Code Reuse rule) — written once in this spec since no prior spec owns it yet.
- **Bounded-AI boundary**: These route handlers contain no model-generated content of their own — they orchestrate calls to spec 008's harness (which does involve a model) but the routing/response-shaping logic itself is deterministic.
- **Verification Oracle**: `npx vitest run tests/integration/apiRoutes.test.ts` — new integration-style tests against the route handlers directly (Next.js Route Handler test harness, or direct function invocation with constructed `Request` objects — no real server needed), with spec 008's `runHarness` and spec 010/010b's `db` layer both faked: (a) **IDOR test, the binding PRD §12 acceptance criterion**: user A creates a run; a request to `GET /api/runs/:id` for that run's ID, authenticated as user B, returns `not_found` (never the run's content, never a response distinguishable from "this ID doesn't exist") — this is the literal test PRD §12 names ("user A's run ID requested under user B's session returns `unauthorized` or `not_found`, never the run"); (b) a request to `GET /api/runs/:id` for the same run, authenticated as user A (the owner), returns the run successfully; (c) a request from an `Origin` header not present in `CORS_ALLOWED_ORIGINS` is rejected on all three endpoints, confirmed by checking the response has no `Access-Control-Allow-Origin` header matching the rejected origin; (d) a signed-in-but-not-allowlisted request (spec 011's `isAllowlisted` returning `false`) is rejected distinctly from an unauthenticated request — reusing spec 011's two-check distinction at the route level, confirming the route handler actually calls both functions rather than just one.
- **Intellectual Control**: Test (a) above is the single most consequence-bearing oracle in this entire Phase-1 build — it is the literal, named reproduction of PRD §9 finding #2 / US-5's acceptance criterion, and it must pass against the *real* route handler code path (not a simplified stand-in), since this is exactly the kind of check that's cheap to get subtly wrong (e.g., checking ownership after already having fetched and partially serialized the response). The shared CORS-check helper being called identically in all three handlers (rather than copy-pasted three times with potential drift) is what keeps "strict, every request" true as a structural fact rather than something that could silently regress in one handler during a future edit.
- **Constraints**: No new dependency. No GitHub write call anywhere in these routes — Phase 1's read-only invariant holds all the way to the HTTP boundary. `message` fields in every error response are the canned plain-language strings from spec 002's error map — never an interpolated raw exception message, confirmed structurally (route handlers catch and map to `ErrorCode`, they don't pass `error.message` through from a caught exception).
- **Edge Cases**: A malformed/missing `issueUrl` body on `POST /api/runs` is rejected before auth even matters as much as input shape — but auth is still checked first in the handler's code order (two-check auth, then input validation, then harness) per the standard ordering TRD §5 prescribes, so an unauthenticated malformed request gets `unauthorized`, not `invalid_url` (don't leak input-validation detail to someone who isn't authenticated to use the endpoint at all). A `GET /api/runs?limit=` with no `limit` query param defaults to a sane bound (e.g., 20) rather than returning unbounded rows or erroring. Concurrent requests to `POST /api/runs` from the same user near the `RUNS_PER_USER_PER_HOUR` boundary are handled by spec 007b's rate limiter's own count-query semantics — this spec doesn't add additional concurrency logic beyond calling that check before invoking the harness.
- **UI States**: N/A — no UI files (these are API route handlers, not UI components).
